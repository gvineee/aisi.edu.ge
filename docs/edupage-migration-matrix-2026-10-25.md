## 4. importer-ის საერთო ინფრასტრუქტურა — **აშენდა 2026-10-25** (ქვემოთ §8)

არსებული `ImportContentRecords` WordPress-ის CMS-ს ემსახურება და სასკოლო მონაცემებს არ ერგება. დასამატებელია:

- **`import_batches`:** `tenant, source=edupage, type, academic_year, file sha256, exported_at, scope/filters, source_version, row counts, mode=dry_run|apply, status, created_by`.
- **`import_identity_map`:** `tenant, source, entity_type, academic_year, source_id → target_type/target_id, source_hash, first/last_batch`. unique `(tenant, source, entity_type, year, source_id)`.
  - ხელახალი გაშვება ახალ ჩანაწერს არ ქმნის, იყენებს არსებულ კავშირს.
  - შეცვლილი წყაროს სტრიქონი hash-ით იცნობა.
  - ჩვენთან შემდგომ ხელით შეცვლილ ველს importer არ გადაწერს: მაგ. თუ `updated_at` > batch, ცვლილება conflict-ად ინიშნება.
- **`import_issues`:** quarantine სტრიქონები (`unresolved_reference`, `duplicate`, `validation`, `conflict`, `unknown_code`). raw მნიშვნელობები აქ არ ინახება, მხოლოდ source ID-ები და ველების სახელები; პირადი მონაცემი log-ებში არ ხვდება.
- **Artisan ბრძანება `edupage:import {type} --tenant= --file= [--apply]`:**
  - ნაგულისხმევად dry-run: მხოლოდ preview და counts;
  - `--apply` სრულდება ერთ transaction-ში თითო batch-ზე;
  - audit: `edupage_import.applied`, რაოდენობებით.
- **რიგი:** წლები → staff/კლასები/საგნები/ოთახები/ჯგუფები → მოსწავლეები/ჩარიცხვები/მეურვეების მოწვევები → ვერსიები/ზარები/განრიგი → თემები/დასწრება → პერიოდები/ნიშნები.
- **ტესტები (სინთეტიკური fixtures):**
  - ორი tenant-ის იზოლაცია;
  - არასწორი reference → quarantine;
  - განმეორებითი import → 0 ახალი;
  - შეცვლილი წყაროს სტრიქონი;
  - ხელით ცვლილების შენარჩუნება;
  - ვერსიის validity და კონფლიქტი;
  - revoked guardian;
  - unassigned teacher;
  - unpublished grades;
  - private download;
  - MySQL და SQLite/Postgres თავსებადობა.

# აისი — ახალი ვებგვერდისა და სასკოლო პლატფორმის სრული პროექტი

ვერსია: 1.0 · 2026-09-10 · სტატუსი: პროექტის შეთავაზება და განვითარების სპეციფიკაცია.

ეს დოკუმენტი აღწერს შესაქმნელ პროდუქტს. ფუნქციები, რიცხვები, ვადები და ტექნიკური მიზნები მოთხოვნები/შეფასებებია და არა არსებული სკოლის სისტემის შესახებ დადასტურებული ფაქტები. არსებული გვერდის კვლევა ცალკე აუდიტშია. დიზაინის მაკეტში მონაცემები სადემონსტრაციოა.

## 1. მთავარი გადაწყვეტილება

შევქმნათ ერთი მართვადი პლატფორმა სამი დამოუკიდებელი გამოცდილებით: საჯარო ვებგვერდი ახალი ოჯახებისთვის; დაცული სასკოლო პორტალი მოსწავლეებისთვის, მშობლებისა და თანამშრომლებისთვის; ადმინისტრირება სკოლის ოპერაციებისათვის. პროდუქტი თავიდანვე ითვალისწინებს სხვადასხვა სკოლის ბრენდს და მონაცემების გამიჯვნას, მაგრამ პირველი გამოშვება ემსახურება აისს. სხვა სკოლების თვითრეგისტრაცია და გამოწერის ბილინგი დაემატება მხოლოდ პირველი სკოლის პილოტის შემდეგ.

რეკომენდებული საფუძველია Laravel 13 + ოფიციალური React starter kit + TypeScript + Inertia + PostgreSQL. Laravel 13 ოფიციალურად გამოშვებულია 2026 წლის 17 მარტს და მოითხოვს PHP 8.3-ს ან უფრო ახალ მხარდაჭერილ ვერსიას. სამუშაო გარემოდ რეკომენდებულია PHP 8.4, ჰოსტინგისა და ყველა დამოკიდებულების შემოწმებით. React-ის ოფიციალური starter kit არსებობს და Inertia-ით ებმება Laravel-ს. ზუსტი minor-ვერსიები პროექტის დაწყებისას ჩაიკეტოს lockfile-ებში. [Laravel releases](https://laravel.com/framework/docs/13.x/releases), [starter kits](https://laravel.com/framework/docs/13.x/starter-kits).

## 4. საჯარო საიტის ინფორმაციული სტრუქტურა

1. მთავარი — მთავარი დაპირება, რეალური სასკოლო ფოტო, პროგრამები, სასწავლო მიდგომა, სკოლის ყოველდღიურობა, მიღება, სიახლე, კონტაქტი.
2. სკოლის შესახებ — მისია, ისტორია, გუნდი, გარემო, ავტორიზაცია/დოკუმენტები მხოლოდ გადამოწმებული მასალით.
3. სწავლა — საფეხურები, სასწავლო მიდგომა, საგნები, ენები, შეფასება და მხარდაჭერა; თითო პროგრამას საკუთარი URL.
4. მიღება — ნაბიჯები, მოთხოვნილი საბუთები, ვადები, საფასური სკოლის გადაწყვეტილების შესაბამისად, ხშირად დასმული კითხვები, ვიზიტი.
5. სასკოლო ცხოვრება — კლუბები, პროექტები, ღონისძიებები, მოსწავლეთა ნამუშევრები შესაბამისი გამოქვეყნების ნებართვით.
6. სიახლეები — თარიღიანი სტატიები, კატეგორიები, საძიებო და არქივი.
7. კალენდარი — მხოლოდ საჯარო ღონისძიებები; კერძო კლასის განრიგი პორტალში.
8. რესურსები — საჯარო წესები, პოლიტიკები, გზამკვლევები და ხელმისაწვდომი ფაილები.
9. კონტაქტი — დადასტურებული მისამართი, ტელეფონი, საათები, ტრანსპორტის ინფორმაცია; რუკა სურვილისამებრ იტვირთება.
10. პორტალში შესვლა — თვალსაჩინო, მაგრამ მთავარი საჯარო CTA რჩება „დაგეგმეთ ვიზიტი“.

ქართული მთავარი ენაა. არქიტექტურაში `ka` და `en` მხარდაჭერა მზად იყოს; ინგლისური არ გამოქვეყნდეს ნახევრად თარგმნილი. URL-ების სტრატეგია: `/ka/...`, `/en/...`, ძველი მისამართებისთვის 301 mapping. მენიუს დამალვა არ ცვლის მომხმარებლის უფლებებს.

## 5. მოდულები და მოთხოვნები

### 5.1 კონტენტის მართვა და მიღება — პირველი გამოშვება

- CMS: ტიპიზებული ბლოკები, მედიაბიბლიოთეკა, alt-ტექსტი, სათაური/აღწერა, slug, მონახაზი, preview, დაგეგმილი გამოქვეყნება, ვერსიები და აღდგენა. არ მივცეთ რედაქტორს შეუზღუდავი JavaScript/HTML.
- მედია: წყარო, ავტორი, ლიცენზია/გამოყენების საფუძველი, ბავშვის ფოტოს ნებართვის ბმული და მოქმედების ვადა. ნებართვის გაუქმება ქმნის მასალის გადახედვის დავალებას.
- მიღების მოკლე ფორმა: მშობლის სახელი, საკონტაქტო საშუალება, სასურველი საფეხური/წელი, თანხმობა/ინფორმაციის მიღების დადასტურება. საწყის ლიდ-ფორმაში არ მოითხოვოს ბავშვის პირადი ნომერი ან სამედიცინო ისტორია.
- ვიზიტები: დროის სლოტები, ტევადობა, დროის დაჯავშნის კონკურენტული დაცვა, გაუქმება/გადატანა, თანამშრომლის პასუხისმგებლობა, შეტყობინებები queue-ით.
- მიღების მდგომარეობები: ახალი → დაკავშირებულია → ვიზიტი → განაცხადი → განხილვა → შეთავაზება → ჩარიცხვა / დახურული. უარი არ იგზავნება დაუდასტურებელი ავტომატური წესით.
- ანტისპამი, rate limit, server validation, დუბლირებული ლიდის გაფრთხილება; ფორმის წარმატება მხოლოდ შენახვის შემდეგ.

### 5.2 იდენტობა და სკოლის სტრუქტურა

- მოწვევით რეგისტრაცია; ვადიანი, ერთჯერადი invitation; ელფოსტის დადასტურება; ანგარიშის აღდგენა; სესიების გაუქმება.
- ადმინისტრატორის, ბუღალტრისა და პლატფორმის ოპერატორის MFA სავალდებულო. მასწავლებლისთვის ეტაპობრივი სავალდებულო rollout.
- სკოლა → კამპუსი → სასწავლო წელი → სემესტრი → კლასი/ჯგუფი → საგანი → საგნის შეთავაზება → მასწავლებლის მინიჭება.
- მოსწავლის ჩარიცხვა წლით და მოქმედების ვადებით; დასრულებული სასწავლო წელი მხოლოდ წაკითხვადი არქივია უფლებამოსილების მიხედვით.
- მეურვე-მოსწავლის კავშირი შეიცავს ცალკე უფლებებს: აკადემიური ინფორმაცია, ფინანსები, წაყვანა/მიღება, შეტყობინებები; ადმინისტრაცია ამოწმებს უფლებამოსილებას.
- სპეციალური მხარდაჭერის/ჯანმრთელობის მონაცემები ცალკე, უფრო ვიწრო ნებართვით; საწყის ფაზაში არ შეგროვდეს, თუ გამართული პროცესიც არ არსებობს.

### 5.3 განრიგი და კალენდარი

- კვირის შაბლონი, კონკრეტული თარიღის ცვლილება, უქმე, ჩანაცვლება, ოთახი, ონლაინ ბმული, ჯგუფების გაყოფა.

### 5.4 დავალებები, დასწრება და შეფასებები

- დასწრება: ესწრება, აგვიანებს, არ ესწრება, საპატიო გაცდენა; ცვლილების ავტორი და მიზეზი; ერთ გაკვეთილზე ერთ მოსწავლეს ერთი ჩანაწერი.

- ელექტრონული ჟურნალის ოფიციალურ სახელმწიფო სისტემასთან ინტეგრაცია ცალკე feasibility სამუშაოა; არ დავპირდეთ API-ს არსებობას ან ოფიციალური ჟურნალის ჩანაცვლებას.

### 5.6 ფინანსები

- server-to-server დადასტურება ხელმოწერის/ავტორიზებული პროვაიდერის API-ით; event ID უნიკალურია; duplicate/out-of-order webhook უსაფრთხოა; tenant განისაზღვრება სანდო merchant mapping-ით.
- გადახდის მდგომარეობა: created → pending → succeeded / failed / expired; refund არის ცალკე ჩანაწერი. დასრულებული გადახდა ვერ გადაიქცევა failed-ად დაგვიანებული webhook-ით.
- provider amount, currency, invoice/merchant reference ერთმანეთს უნდა ემთხვეოდეს; შეუსაბამობა გადადის ხელით განხილვაში.
- დარიცხვის და ჩარიცხვის რეესტრი უცვლელი entries-ით; შესწორება reversal/credit-ით; ფულის განაწილება transaction-ში, race protection-ით. ინვოისის ჯამი და გადახდის allocation არასოდეს კარგავს თეთრებს.
- ყოველდღიური შეჯერება, უცნობი ჩარიცხვების სია, partial payment, overpayment, bank transfer, უკუგადახდა; რეალური refund მოქმედებისთვის ფინანსური უფლებამოსილება და დამტკიცების პოლიტიკა.
- ეს არის სკოლის ანგარიშსწორების მოდული; საგადასახადო დოკუმენტის კანონიერ ფორმას და ბუღალტრული ექსპორტის წესს ადგილობრივი სპეციალისტი ადასტურებს.

## 7. არქიტექტურა

**მოდულური მონოლითი:** ერთი Laravel აპლიკაცია, საერთო identity და მკაფიო domain მოდულები: Tenancy, Identity, Content, Admissions, Academics, Timetable, Learning, Library, Finance, Communications, Reporting. Domain services/action classes მართავს პროცესებს; controller მოკლეა; authorization policies და Form Requests ყველა შესაბამის შესასვლელშია. თავიდან მიკროსერვისები არ გვჭირდება.

React + Inertia ინარჩუნებს ერთ routing/auth მოდელს და ამარტივებს Laravel-თან მუშაობას. საჯარო გვერდებს მიეწოდოს სერვერზე რენდერებული HTML (Inertia SSR ან მიზანმიმართული Blade საჯარო rendering გადაწყვეტილების დოკუმენტით), რათა სათაური/კონტენტი/metadata გამოჩნდეს crawler-სთვის JS-ის გარეშეც. პორტალისთვის არ გვჭირდება ცალკე საჯარო API; მომავალი მობილური აპისთვის `/api/v1` დაემატება რეალური მოთხოვნისას.

ინფრასტრუქტურა: PostgreSQL, Redis queue/cache, S3-compatible private/public storage განცალკევებით, transactional email, CDN მხოლოდ საჯარო ფაილებისთვის, scheduled jobs, error monitoring. Horizon ან სხვა queue supervisor შეირჩეს გარემოს მხარდაჭერის მიხედვით. Node build runtime და SSR worker-ის საჭიროება გათვალისწინდეს deployment-ში.

### 7.1 White-label და tenant isolation

პირველი სკოლის შემთხვევაშიც შეიქმნას `tenants`, `tenant_domains`, `tenant_memberships`, `brand_settings`, `feature_entitlements`. აისის სახელი, ლოგო, ფერი, საკონტაქტოები და ტექსტი seed/config data-ა; კომპონენტებში არ ჩაიკეროს.

საწყისი სტრატეგიაა საერთო PostgreSQL ბაზა `tenant_id`-ით. ყველა tenant-owned ცხრილში tenant_id სავალდებულოა; membership განსაზღვრავს როლს კონკრეტულ სკოლაში. Cross-tenant ურთიერთობების ასარიდებლად composite foreign keys/unique constraints გამოიყენეთ, სადაც პრაქტიკულია. ყველა მოთხოვნა იწყება სანდო hostname/domain mapping-ით და ავტორიზებული membership-ით; მოთხოვნის body-ში მოწოდებული tenant_id არ არის სანდო.

Eloquent scope მხოლოდ დამხმარეა და არ არის იზოლაციის ერთადერთი გარანტია. Policy, relation query, route binding, validation exists/unique, exports, search, raw query, notifications, cache keys, storage paths და jobs tenant-aware უნდა იყოს. Queue job ატარებს tenant ID-ს, ამოწმებს tenant-ს და ბოლოს ასუფთავებს context-ს. Worker-ზე ერთი სკოლის context არ უნდა დარჩეს მომდევნო job-ისთვის. PostgreSQL RLS შესაძლებელია დამატებით მხოლოდ connection-pooling/context-reset ტესტების შემდეგ; დაუტესტავი RLS არ გამოცხადდეს დაცვად.

სკოლა ირჩევს ლოგოს, favicon-ს, ფერების დაშვებულ token-ებს, შრიფტის whitelist-ს, ენას, დომენს, დროის სარტყელს, პროგრამების სახელებს, შეფასების სკალას და ჩართულ მოდულებს. თემა ვერ დაამატებს arbitrary script-ს. custom domain მოითხოვს მფლობელობის გადამოწმებას და TLS-ს; ძველი დომენის მოხსნისას cache/routes განახლდეს.

დამოუკიდებელი database-per-tenant ვარიანტი მოგვიანებით, თუ ხელშეკრულება/მასშტაბი მოითხოვს; ამის გამო ახლავე repository abstraction-ების ზედმეტი ფენები არ ავაშენოთ. მეორე tenant-ის seed და იზოლაციის ტესტები თავიდანვე სავალდებულოა. მოსწავლის სწავლის გადასახადი და სკოლისთვის SaaS გამოწერა სხვადასხვა ფინანსური კონტექსტია.

## 9. უსაფრთხოება და არასრულწლოვანთა მონაცემები

ეს არის საინჟინრო მოთხოვნები; საქართველოს მოქმედ მოთხოვნებთან საბოლოო შესაბამისობას სკოლის პასუხისმგებელი პირი/იურისტი ადგენს. პროექტი არ აცხადებს სამართლებრივი აუდიტის დასრულებას.

- შეადგინეთ მონაცემთა კატალოგი: ველი, მიზანი, წვდომა, დამუშავების საფუძვლის დასადასტურებელი პასუხისმგებელი, შენახვის ვადა, წაშლის/არქივის წესი. ვადები არ გამოიგონოთ.
- TLS, secure/HttpOnly/SameSite cookies, CSRF, login throttling, MFA, სესიის ხელახალი დადასტურება მაღალი რისკის მოქმედებებზე, password reset-ის ერთჯერადი token.
- server-side authorization ყოველ read/write/download/export endpoint-ზე; აგრეთვე job-ებში. ნაგულისხმევი პასუხია deny.
- ჯანმრთელობა და განსაკუთრებული საჭიროებები განცალკევებული ნებართვით/დაცვით. მასობრივი ექსპორტი შეიცავს მხოლოდ მიზნისთვის აუცილებელ ველებს.
- audit: ვინ, რომელი tenant, როდის, რა ობიექტი/მოქმედება, მიზეზი; არ ჩაიწეროს პაროლი, token, ბარათის მონაცემი ან მთლიანი პირადი დოკუმენტი.
- გამოქვეყნებამდე ფოტოების უფლებების დადასტურება; მოსწავლის სახელი და ფოტო ერთ პოსტში მხოლოდ დამტკიცებული პოლიტიკით.

## 10. მობილური, ხელმისაწვდომობა და ხარისხი

ვიზუალური მიმართულება: განათებული, მშვიდი, ქართული ტიპოგრაფიით; დიდი კონტენტი, მკაფიო კონტრასტი, ბრენდის მზის/აისის მოტივი. საჯარო გვერდს სჭირდება თავისუფალი სივრცე და ერთი მთავარი მოქმედება; პორტალს — კომპაქტური ყოველდღიური ამოცანები. მობილურზე ქვედა ნავიგაცია მაქსიმუმ ხუთი პუნქტით და safe-area padding-ით.

სავალდებულო მდგომარეობები: loading, empty, validation error, permission denied, network failure, expired session, success, unsaved changes. ფინანსურ მოქმედებას ჰქონდეს pending მდგომარეობა; დიზაინში ღილაკის დაჭერა არ უნდა ნიშნავდეს წარმატებულ გადახდას.

ხელმისაწვდომობის სამიზნეა WCAG 2.2 AA: კლავიატურა, ხილული focus, სწორი labels და headings, contrast, ეკრანის წამკითხველი, reduced motion. პროექტის touch target სამიზნე 44×44 CSS px-ია. სტატუსი მხოლოდ ფერით არ გამოიხატოს; გრაფიკს ახლდეს ტექსტური/ტაბულარული ალტერნატივა. [W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/).

პროექტის performance budgets (საწყისი სამიზნე, გასაზომი რეალური მოწყობილობით): საჯარო მთავარის LCP ≤2.5 წმ, CLS ≤0.1, INP ≤200 მწმ p75-ზე; ოპტიმიზებული hero asset, responsive images, self-hosted/subset Georgian font ლიცენზიის შემოწმებით. პორტალის ჩვეულებრივი read request p95 ≤500 მწმ შეთანხმებულ დატვირთვაზე; დატვირთვის საწყისი ტესტი 100 ერთდროულ აქტიურ სესიაზე, რაც სკოლის ნამდვილ მასშტაბთან დაზუსტდება.

PWA: manifest, ინსტალაციის affordance, offline fallback. პირველ გამოშვებაში პირადი მონაცემები, ნიშნები და ფინანსები offline cache-ში არ ჩაიწეროს; service worker მხოლოდ სტატიკურ assets-ს მართავს. logout-ისას სენსიტიური UI state გასუფთავდეს. „აპის მსგავსი“ ვიზუალი არ ნიშნავს App Store/Play Store native აპს.

3. მასწავლებელი სხვა კლასის ნიშნებს ვერ ცვლის; unpublished grade არ გაეცემა მოსწავლეს/მშობელს.
4. ერთი ოთახის ან მასწავლებლის გადაფარვადი განრიგი არ ქვეყნდება; ჩანაცვლება სწორი მიმღებებისთვის ჩანს.
5. duplicate webhook ერთ payment-ს ქმნის; out-of-order არ ანგრევს სტატუსს; თანხის/ვალუტის სხვაობა არ ჩაითვლება გადახდილად.
6. პარალელური გადახდა/დათმობა არ იწვევს ზედმეტ allocation-ს; refund და reconciliation ანგარიშები თანხვედრაშია.
7. კერძო ფაილის direct URL გამოუვალია; expired signed URL არ მუშაობს; განსხვავებულ tenant-ს policy უარს ეუბნება.
8. 360px, 390px, 768px და 1440px ეკრანებზე არ არის გვერდის ჰორიზონტალური overflow; ცხრილებს აქვთ მობილური ალტერნატივა ან საკუთარი scroll region.
9. მიღების ფორმა და პორტალის მთავარი გზები სრულდება კლავიატურით; errors ეკრანის წამკითხველს ეცნობება.
10. backup რეალურად აღდგა staging-ში; smoke test-მა გაიარა; deployment rollback პროცედურა შესრულებადია.
11. საჯარო გვერდის სათაური, აღწერა და ძირითადი ტექსტი HTML-შია; sitemap/robots/canonical/hreflang სწორი, private გვერდები არ ინდექსირდება.
12. დემო სახელები, ციფრები, ფოტოები და მარკეტინგული მტკიცებები წარმოებაში მხოლოდ გადამოწმების შემდეგ იცვლება რეალურით.

## 12. მიგრაცია, გაშვება და ოპერირება

ძველი საიტიდან შეიქმნას URL/content inventory: ძველი მისამართი, სათაური, მასალის მფლობელი, ფაილები, სტატუსი keep/rewrite/archive, ახალი URL, redirect. მოიპოვეთ CMS export/backup და სკოლის დადასტურებული მედია. საიტის უბრალოდ scraped ტექსტი არ არის სრული მონაცემთა მიგრაცია.

რეპეტიცია staging-ში: ტექსტების/მედიის import → დუბლიკატების შემოწმება → redirect crawl → ქართული ძიება → მობილური QA → სკოლის UAT. კონტენტის freeze მოკლე ფანჯარაში, ბოლო delta migration და snapshot. სკოლის ძველი საფოსტო MX/TXT ჩანაწერები DNS გადართვისას შენარჩუნდეს.

CI: dependency install locked versions, lint, TypeScript, build, backend tests, security-critical integration tests, browser smoke. deployment: backup → backward-compatible migration → release switch → worker restart → cache/SSR health → smoke. მონაცემების დესტრუქციულ ცვლილებებს ცალკე migration გეგმა და backup სჭირდება; rollback მხოლოდ კოდის დაბრუნება ყოველთვის არ არის საკმარისი.

მიზნობრივი ოპერაციული პარამეტრები დასამტკიცებლად: uptime 99.9%; პორტალის RPO ≤24სთ და RTO ≤4სთ, ფინანსური მონაცემებისთვის უფრო მკაცრი RPO პროვაიდერის reconciliation-ით/ბაზის point-in-time recovery-ით. რეალური SLA ჰოსტინგისა და ხარჯის არჩევის შემდეგ ჩაიწეროს; ეს რიცხვები მიმდინარე გარანტია არ არის.

Monitoring: failed jobs, email delivery, webhook lag, reconciliation differences, error rate, storage და DB მოცულობა, backup age, certificate expiry. პასუხისმგებელი იყოს კონკრეტული ადამიანი/გუნდი; alert-ის გაგზავნა თავისთავად incident response არ არის.

გაშვების წინ ტრენინგი: რედაქტორის 1 სესია, მასწავლებლის ჟურნალი/დავალება 1 სესია, ფინანსების ცალკე სესია, მშობლის მოკლე ქართულენოვანი გზამკვლევი. პილოტის პირველი 2 კვირა მხარდაჭერის განსაზღვრული არხით.

## 13. გასაყიდი პლატფორმის შეფუთვა

სამუშაო პროდუქტის სახელი საბოლოოდ ცალკე გადაწყდეს; „აისი“ პირველი სკოლის ბრენდია. ერთ codebase-ზე შესაძლებელი იყოს Website, School Portal, Finance მოდულების შეთავაზება. გეგმა განსაზღვრავს entitlement-ს და არა მხოლოდ მენიუში ღილაკის არსებობას; backend enforce აუცილებელია. ფასები დადგინდეს ბაზრის კვლევის, აქტიური მოსწავლეების, storage/SMS და მხარდაჭერის ხარჯის შემდეგ.

ყოველი tenant onboarding მოიცავს დომენს, ბრენდს, ლოკალს, სასწავლო წელს, როლების მოწვევას, CSV import-ს, მონაცემთა წესებს და საცდელ პილოტს. offboarding მოიცავს უფლებამოსილ export-ს, დომენის გათავისუფლებას, შეთანხმებულ შენახვა/წაშლას და backup-ის lifecycle-ს. სკოლის subscription-ის შეჩერებამ არ უნდა შექმნას ბავშვის მონაცემების უკონტროლო დაკარგვა; read-only/grace period შეთანხმდეს ხელშეკრულებით.
